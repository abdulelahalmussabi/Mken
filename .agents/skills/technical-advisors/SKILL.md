# المستشارون التقنيون (Technical Advisors)

هذه مهارة مرجعية تُغطّي عشر قدرات استشارية. كل قدرة = قسم أدناه: متى تُستخدم، الأدوات/الملفات المعنية في مكّن، خطوات التنفيذ المرجعية، وأمثلة. اقرأ القسم المعني عند الحاجة فقط — لا حاجة لقراءة كل شيء دفعة واحدة.

قاعدة عامة: مشروع مكّن = Vercel serverless (`api/*.js` CJS) + Supabase (Postgres/Auth/RLS) + WhatsApp Cloud API + Moyasar + واجهات HTML/JS. راجع مهارة `mken-saas` لتفاصيل البنية الأساسية قبل أي عمل استشاري.

---

## 1. استدعاء الأدوات والدوال (Function Calling)

**متى:** عند تنفيذ أمر برمجي، استعلام API خارجي، أو تشغيل أداة داخل سيرفر/إدارة مكّن.

**الأدوات المتاحة:** Bash (تنفيذ)، Read/Edit/Write (ملفات)، WebSearch/WebFetch (خارجي)، MCP tools (Android، Browser، node_repl).

**خطوات مرجعية:**
1. حدّد إن كان العمل محلياً (Bash/Read) أم خارجياً (WebFetch لـAPIs موثقة).
2. للأوامر على مشروع مكّن: نفّذ من جذر `D:\de7me\mken`، واستخدم Git Bash على ويندوز.
3. لاستعلام API داخل المنصة: اقرأ أقرب `api/*.js` لنسخ نمط Auth/CORS/Supabase client.
4. المكالمات المستقلة شغّلها بالتوازي في رسالة واحدة.

**مثال:** استعلام حالة Vercel deploy:
```bash
vercel ls 2>/dev/null | head -5 || echo "vercel CLI غير مثبت محلياً"
```

## 2. استرجاع المعرفة المدعوم بالبحث (RAG)

**متى:** السؤال عن وثيقة/سلوك غير معروف بدقة، أو تجنّب التخمين في تفاصيل API/SQL.

**الأدوات:** WebSearch + WebFetch (وثائق عامة)، Read/Grep/Glob (داخل المشروع).

**خطوات مرجعية:**
1. ابحث داخل المشروع أولاً (الأسرع والأدق): `Grep` لكلمة مفتاحية، `Glob` لاسم ملف.
2. إن لم يوجد، ابحث في الويب بمصطلح دقيق (اسم المكتبة + إصدار + ظاهرة).
3. اقرأ المصدر الرسمي عبر WebFetch، واقتبس `file:line` أو الرابط.
4. **لا تخمّن** توقيع API أو سلوك SQL — إن لم تجد، قل "لم أجد مرجعاً موثوقاً" واقترح كيفية التحقق.

**نمط مكّن:** حالات RAG الشائعة — سلوك WhatsApp webhook (`api/whatsapp-webhook.js`)، حقول جدول Supabase، إعدادات tenant في `data/tenants/*.json`.

## 3. تحليل وفحص الكود (Code Analysis & Debugging)

**متى:** اكتشاف ثغرة، تحديد سبب عطل، مراجعة PR، أو فهم كود غريب.

**خطوات مرجعية:**
1. ابدأ بقراءة الملف كاملاً قبل التعديل (القاعدة الأساسية للـEdit tool).
2. تتبّع مسار البيانات: من أين يأتي الـinput؟ إلى أين يصل؟ (مثلاً webhook → handler → DB).
3. ابحث عن anti-patterns مكّن المعروفة: مفاتيح Supabase service role في كود واجهة، RLS معطّلة، tenant غير مُحلّ من subdomain، CJS/ESM مختلط.
4. للأعطال: اقرأ رسالة الخطأ كاملةً، حدّد آخر نقطة عملت، ثم ابحث عن السبب الجذري لا العرض.
5. اعرض النتيجة بمرجع `file:line`.

**مثال مكّن شائع:** عطل "tenant undefined" غالباً من نسيان resolve subdomain في handler جديد — تحقّق من نمط `api/_lib/`.

---

## 4. تصميم المعماريات (System Architecture Design)

**متى:** اقتراح بنية جديدة، إضافة نظام كامل (مثل fleet tracking أو marketplace)، أو تقييم قابلية توسّع.

**خطوات مرجعية:**
1. ارسم الطبقات: Frontend → API → DB → External services. لكل طبقة اذكر الموقع في مكّن.
2. اربط بمكوّنات مكّن الموجودة: Supabase (Postgres)، Vercel serverless، WhatsApp، Moyasar، n8n workflows في `data/`.
3. للبنى السحابية (AWS/GCP/Azure): قارن بالحل القائم على Vercel+Supabase، واذكر متى يكون الانتقال مبرّراً (تكلفة، تحكّم، امتثال).
4. اذكر دائماً: **multi-tenancy** (كيف يُعزل كل tenant)، **الأمان** (RLS، مفاتيح server-side)، **التكلفة التقريبية**، **نقاط الفشل المنفردة**.

**نمط مكّن:** كل schema جديد (`db/*.sql`) يبدأ بـ`tenant_id` ويُفعّل RLS. راجع `db/loyalty-iso20022-schema.sql` كنموذج.

---

## 5. إدارة قواعد البيانات (Database Querying)

**متى:** كتابة/شرح SQL أو NoSQL، استخراج بيانات هيكلية، تصميم schema.

**السياق مكّن:** Supabase = PostgreSQL. المخططات في `db/*.sql`. بيانات tenants في `data/tenants/*.json` وSupabase.

**خطوات مرجعية:**
1. اقرأ أقرب schema مرتبط (`Glob db/*.sql`) لمعرفة الجداول والأعمدة الفعلية قبل الكتابة.
2. كل استعلام على بيانات tenant يجب أن يفلتر بـ`tenant_id` (مع RLS كشبكة أمان).
3. للعمليات الكبيرة: `EXPLAIN ANALYZE` أولاً، فواصل `select` (`RETURNING`) في UPDATE/DELETE.
4. للتجربة المحلية: `scripts/*.cjs` (مثل `query-tenant-config.cjs`) أنماط جاهزة للاتصال بـSupabase.
5. **لا** تُدخل service-role key في واجهة؛ استخدم anon key + RLS للعمليات من المتصفح.

---

## 6. تحليل ملفات السجل (Log Analysis & Observability)

**متى:** تتبّع أعطال الإنتاج، تحليل أداء، فهم سلوك cron.

**مصادر السجلات في مكّن:**
- Vercel: dashboard → Functions → Logs (للـ`api/*.js`).
- Supabase: dashboard → Logs (Postgres, Auth, Edge).
- WhatsApp: `js/admin-whatsapp-logs.js` لواجهة الإدارة + Vercel logs للـ`api/cron-whatsapp.js`.
- Android: `adb logcat` أو أداة `android_logs` MCP.

**خطوات مرجعية:**
1. حدّد الطبقة (API/DB/WhatsApp/Android) ثم المصدر المناسب.
2. فلتر بالوقت أول ثم بـ`applicationId` أو tenant.
3. ابحث عن: error level، stack trace، timestamps متقاربة (race condition)، 4xx/5xx المتكررة.
4. اربط الخطأ بالكود عبر `file:line`، واقترح إصلاحاً.

## 7. الأمن السيبراني والامتثال (Cybersecurity & Audit)

**متى:** مراجعة أمان، تطبيق OWASP/PDPL، تدقيق مفاتيح وصلاحيات.

**خطوات مرجعية (قائمة تدقيق مكّن):**
1. **الأسرار:** `grep -riE "service_role|secret|sk_live|token" api/ js/` — يجب ألا تظهر في واجهة.
2. **RLS:** كل جدول tenant له RLS مفعّل بسياسة `tenant_id = auth.uid()` أو ما يكافئها. تحقّق عبر `db/*.sql`.
3. **Auth:** Supabase Auth مفضّل على ADMIN_PIN الثابت. راجع `api/v1/auth.js`.
4. **Inputs:** تحقّق من كل input خارجي (webhook، query params) قبل الاستخدام.
5. **PDPL (السعودية):** تصنيف البيانات الشخصية، حق الطلب/الحذف، تسجيل الوصول. راجع `api/v1/pdpl/`.
6. **Payments:** التحقّق من Moyasar webhook signature server-side (`api/moyasar-webhook.js`).
7. أبلغ عن الثغرات بـ`file:line` + خطورة (Critical/High/Medium/Low) + الإصلاح المقترح.

## 8. صياغة مواصفات المنتجات (PRD Generation)

**متى:** تحويل متطلب عمل لوثيقة تقنية، تخطيط ميزة قبل البناء.

**قالب PRD (مكيّف لمكّن):**
```
## [اسم الميزة]
**السياق:** ما المشكلة؟ من المتأثر؟
**الأهداف:** 3-5 نتائج قابلة للقياس.
**المستخدمون:** tenant admin / عميل نهائي / فريق مبيعات.
**التدفقات:**
  1. مسار سعيد (happy path)
  2. حالات حدّية
**المعمارية:**
  - Frontend: <ملف/صفحة>
  - API: <api/*.js جديد أو معدّل>
  - DB: <schema/جدول> + RLS
  - تكاملات: WhatsApp / Moyasar / n8n
**معايير القبول:** قائمة تحقّق.
**المخاطر والاعتبارات:** أمن، تكلفة، multi-tenant.
**خطة التنفيذ:** مراحل مرتبة.
```
أبقِ PRD مختصراً وقابلاً للتنفيذ — تجنّب الإطالة الفضفاضة.

## 9. تقييم ومقارنة التقنيات (Tech Stack Benchmarking)

**متى:** اختيار مكتبة/إطار، تبرير قرار تقني، مقارنة حلول.

**خطوات مرجعية:**
1. حدّد المعايير ذات الصلة بمكّن: توافق Vercel serverless، حجم الحزمة (للأداء)، توافق multi-tenant، تكلفة، نضج/دعم عربي/RTL.
2. قارن 2-4 خيارات في جدول (مكتبة | إيجابيات | سلبيات | توافق مكّن).
3. اذكر دائماً **قراراً مقترحاً** مع السبب، لا مجرد سرد.
4. اربط بالحل القائم — تكلفة التبديل من Vercel+Supabase عالية ومبرَّرة فقط لحاجة قوية (امتثال، تكلفة حجم، تحكّم).

## 10. أتمتة خطوط الإنتاج (DevOps & CI/CD)

**متى:** إعداد/إصلاح نشر، أتمتة اختبار، إدارة بيئات.

**السياق مكّن:** النشر عبر `vercel --prod`، cron في `vercel.json`، لا CI/CD repo ملف مزعوم (تحقّق من `.github/` إن وُجد).

**خطوات مرجعية:**
1. بعد أي تغيير في env: **Redeploy إلزامي** على Vercel.
2. cron handlers (`api/cron-*.js`) يجب أن تكون **idempotent** (تعمل بأمان لو شغّلت مرتين) وتفشل بأمان عند نقص env.
3. للمهام المجدولة: استخدم `CronCreate` (الأداة) لجدولة العمل المحلي، لكن الإنتاج عبر `vercel.json`.
4. الاختبار قبل النشر: شغّل محلياً، تحقّق من webhook يدوياً، ثم انشر.
5. لا تنشر مفاتيح أو `.env`.

## قواعد الاستجابة

- ردّ بالعربية ما لم يكتب المستخدم بالإنجليزية.
- أبقِ أسماء الملفات، مسارات، وأسماء متغيرات البيئة دقيقة وحرفية.
- اقتبس `file:line` عند الإشارة لكود.
- ميّز دائماً بين **ما هو مبني فعلاً في مكّن** و**ما هو اقتراح جديد**.
